# AuthBand Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Execution method awaits the user's choice; do not dispatch agents merely because this header mentions them.

**Goal:** Deliver an iOS 27 authenticator manager and an offline Xiaomi Smart Band 10 authenticator with editable account groups, QR/manual import, and protected synchronization.

**Architecture:** A Swift package owns OTP, import, vault rules, and sync state. SwiftUI owns phone workflows, while one Vela page renders horizontal groups and vertical account lists. Preserve the proven Xiaomi transport and add a separately protected application channel; reading codes never depends on Bluetooth.

**Tech Stack:** SwiftUI, CryptoKit, Security/LocalAuthentication, AVFoundation, Vision/PhotosUI, CoreBluetooth, Vela UX/JavaScript, Node tests, XcodeGen, Xcode 27, existing BlueBand protocol/session code.

**Spec:** [Approved AuthBand design](../specs/2026-10-10-authband-design.md).

**Status:** User approved this plan and inline implementation on 2026-10-10, with an independent review at the end. Implementation is in progress. Hardware acceptance is tracked separately from software verification.

## Global Constraints

- iOS deployment target 27.0; validate Xcode 27/iOS 27 explicitly. One iPhone vault and one paired band.
- TOTP SHA-1/SHA-256/SHA-512; 6 or 8 digits; integer period 15 through 120 seconds, default 30.
- At most 100 phone accounts; 50 selected band accounts; 8 groups; 20 selected accounts per band group. Validate before import/save/sync.
- Vietnamese UI labels; preserve Unicode issuer/account text. No HOTP, Steam codes, push approvals, cloud sync, passkeys, or multiple-band support.
- Default newly imported accounts to phone-only. One account belongs to one group; deleting a group moves accounts to the undeletable default group.
- Face ID/device-passcode phone unlock; obscure UI when inactive. No recurring band PIN prompt by default.
- Explicit foreground BLE sync and disconnect; no location permission, background BLE dependency, RPK installer, or AuthKey extraction.
- One Vela page, `interconnect.instance()` in `onReady`, direct `result.status`, cleanup callbacks/timers. No router transition per tab.
- Native 212 by 520 band layout; title x=40..172/y=46..78, list x=20..192/y=100..414, indicator x=76..136/y=454..470; rows about 136 pixels. Use the baseline mask and verify typography physically.
- Black background, white codes, neutral labels, mint progress, amber expiry, red errors. Fixed code dimensions; no cropped digits, gradients, blur, decorative containers, or image streaming.
- One outstanding sync chunk, maximum 512 encoded UTF-8 envelope bytes. Transport ACK is not durable commit.
- Preserve Xiaomi framing/authentication/crypto compatibility vectors. Never log keys, OTPs, QR data, nonce/key derivations, or raw captures.
- `system.crypto` is unsupported on Band 10 according to inspected vendor documentation. Use established JS primitives, not custom hash/cipher implementations.
- Real-secret provisioning stays disabled until protection, persistence, and firmware acceptance pass. Public RFC fixtures are permitted in the capability build only.
- First useful offline code target <1 second; tab response <150 ms; foreground boundary update <250 ms. Record cold/warm p50/p95/max on actual firmware; automated tests do not establish these targets.
- Work only in AuthBand. Read blueband-ios and blueband-map as baselines. Never revert their existing changes or bind the new build to absolute baseline paths.

## Review Focus

1. A camera callback or background sync finishes after phone lock: no secrets reappear or commit using invalidated state (Tasks 6, 7, 10).
2. Protobuf defaults, URL-encoded `+`, and identical/conflicting QR rescans: preserve correct bytes and reject ambiguity without losing prior batch progress (Task 5).
3. Power fails during deletion or after writing data but before commit: an acknowledged deleted account never returns after recovery (Tasks 8, 10).
4. The clock changes while the band sleeps: stale codes are never displayed as current on wake, and timezone changes do not shift TOTP (Tasks 2, 9).
5. Long Vietnamese labels and diagonal swipes at list edges: identifiers remain distinguishable and gestures do not trap the user or clip codes (Tasks 7, 9, 11).

## Shared Interfaces

Swift declarations live in the task that first produces them. JS wire models use the same field names and integer constraints.

- `OTPAlgorithm` cases are `sha1`, `sha256`, `sha512`. `OTPParameters(algorithm: OTPAlgorithm, digits: Int, period: Int)` validates construction. `TOTPCode` contains `value: String`, `validFrom: Int64`, `validUntil: Int64` in Unix seconds.
- `SecretBytes.init(_ bytes: Data) throws` encapsulates `Data` with redacted description; `AccountID` and `GroupID` are UUID wrappers. `OTPAccount` contains `id`, `issuer`, `label`, `secret`, `parameters`, `groupID`, `order: Int`, `onBand: Bool`.
- `AccountGroup` contains `id`, `name`, `order`, `isDefault`; `Vault` contains schema version 1, `vaultID: UUID`, `revision: UInt64`, groups, accounts. Wire revisions/epochs are canonical decimal strings, bounded at 2^53-1; reject overflow instead of rounding.
- `VaultStore.load() async throws -> Vault?`, `save(_ vault: Vault) async throws`, `lock() async`; `VaultRepository` serializes domain edits and increments revision once per successful transaction.
- `ImportCandidate` is an account before IDs/group assignment; `ImportIssue` identifies record index and a nonsecret reason. `ImportPreview` includes candidates, duplicates, issues and batch readiness. `BatchProgress` has `receivedPartCount: Int`, `totalPartCount: Int`, `isComplete: Bool`.
- `BandSnapshot` contains schema 1, vault ID/revision, selected accounts and their groups/order. `CommittedState` contains vault ID/revision and snapshot digest, with no secret/account labels.
- `ApplicationLink.send(topic: String, body: [String: JSONValue]) async throws` awaits delivery only; `events() async -> AsyncStream<ApplicationLinkEvent>` carries received messages/disconnects. Adapter consumes BlueBandKit, without changing its wire behavior.
- `ProtectedChannel.seal(topic: String, payload: Data) throws -> ProtectedFrame`; `open(_ frame: ProtectedFrame) throws -> ProtectedMessage`. `ProtectedMessage` exposes authenticated topic/payload/sequence and is the only input accepted by the production sync coordinator.
